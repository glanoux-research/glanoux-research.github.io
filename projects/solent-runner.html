The voyage so far

Six phases, each answering a question the last one raised: can you visualize it live, can you predict something the sensors don't say directly, can more than one thing use that prediction, is any of it actually true, what does the weather do to it — and can the twin tell you what to do about it.

Checked against a real ship

Fitted the same curve shape against FuelCast, a public dataset of real high-frequency sensor telemetry. Weather, and a detector that lied

Wind and waves add propulsion power independent of hull condition. The coefficients were fitted against FuelCast by analysis/calibrate_weather.py, and the functional form was chosen by how well each candidate extrapolates from calm into rough weather, not by in-sample fit.

FormIn-sample R²Calm → rough RMSE
Multiplicative on speed³0.95010.1216
Added resistance × speed — chosen0.94830.0972
Constant in speed0.94730.0961

The best in-sample fit was the worst out of range: its extra speed term absorbs speed mis-specification, the same trap that produced the wrong first calibration. The last two forms were within 1% of each other, so the tie was broken on physics: a constant term would charge a weather penalty to a ship at rest. The chosen form, (0.5419·H² + 0.0652·U²)·d(θ)·V, goes to zero with speed. Here d(θ) runs from 1 for weather dead ahead to 0 for weather astern.

Then the fouling detector broke. With weather in the simulator, a calm-water reference blamed a Beaufort 5 headwind on the hull. It raised elevated — monitor on a clean ship, estimating 6.5% excess burn against 1.4% true. That is a textbook confounder, and both standard fixes are now in model/performance.py. One is a weather-aware reference. The other is an ISO 19030-style good-weather filter, which on an all-rough passage correctly returns no answer rather than a wrong one. The detector was never measuring fouling. It was measuring everything it could not explain.

Plan a crossing

From a burn rate to a voyage total: model/voyage.py integrates fuel leg by leg along Le Havre → Southampton (106 nm, three legs). The ship turns, so one fixed wind gives a different penalty on each leg. This panel runs a line-for-line port of that module, checked against the Python to 0.1 L. The twin then recommends the fastest speed that still arrives with a 10% reserve. That step from reporting to recommending is the move to a prescriptive twin.

Does the prediction hold?

analysis/backtest_foc.py replays recorded telemetry and scores each predictor on instantaneous L/h and on the voyage total.

Weather-aware + true fouling (upper bound)——0.08%+0.00%

What this does and does not prove. The simulator burns fuel with the same functional form the twin predicts with, so this cannot validate the physics, which is the same on both sides. It does test everything built on top. Hull condition is recovered from telemetry alone (on the fouled run, 29% error drops to under 1%). The excess-burn → propulsion-penalty conversion is right. The leg integration is sound. The physics itself was checked separately, against real vessel data. The script prints this caveat itself.

How it was built

Fifteen commits over 10 days (21–31 Aug 2026), about 1,550 lines of Python and C#. Each phase was committed separately, and every analysis that changed the model is reproducible from a script in analysis/.

Problems worth mentioning. The first fuel recalibration reached the wrong conclusion (blaming the exponent), and only a joint fit found the missing hotel load. The Unity scene was silently discarded for five days because it was being built in Play Mode, which Unity treats as a sandbox. Dashboard charts flickered because they had no stable keys, and WebGL map traces rendered blank until they were swapped for SVG.

Two kinds of twin

This project sits at the opposite end of a spectrum from something like an NVIDIA Omniverse naval twin — not a smaller version of the same thing, a different question entirely.

This twin — operational

Input
Scalar telemetry — speed, rpm, fuel rate
Model
One algebraic curve, fitted to ~60k rows
Output
Fuel range, ETA, a deviation percentage
Hardware
A laptop, CPU only
Question
Is this ship burning more than it should, right now?

Omniverse naval — design/engineering

Input
3D hull geometry (OpenUSD/CAD)
Model
A neural surrogate trained on thousands of CFD runs
Output
Pressure fields, wake, wave patterns over the hull
Hardware
2× RTX GPUs ≥40GB, 128GB RAM
Question
How will this hull shape perform before we build it?

Next legs

The twin now predicts and prescribes. What it still cannot do is say how sure it is, and the claim that real data could replace the simulator without touching anything downstream has never been tried.

07

Quantify uncertainty

Fuse readings with a Kalman filter or smoother instead of trusting get_latest(1), put error bars on range, ETA and FOC, and detect stale telemetry.

08

A real test suite

The FOC backtest exists. Unit tests do not yet: the detector on synthetic clean and fouled runs, geodesy against known distances, the API schema round-trip, and sensitivity to the hand-picked constants.

09

Swap in real data

Replay FuelCast (or a live AIS feed) through the ingestion layer and change nothing in model/, viz/, api/ or unity/. If anything else has to change, the abstraction leaked.

10

Currents & what-if

Currents change speed over ground, not burn rate: a 2 kn head current costs about 12.5% on this route. Add them next, then fork-and-run-forward "what if we hold 20 kn?" simulation from the current state.
